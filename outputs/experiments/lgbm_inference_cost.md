# LightGBM 推理成本 —— 评测环境跑得完吗

评测环境 **4 核 / 12GB / 无 GPU**，超时该 time_id 置 0。
按真实形态计时：一个 time_id 一批（平均 15.0 行）、500 次调用外推到 214,538 次。

> 15 行是极小批 —— **LightGBM 的每次调用固定开销很可能盖过树遍历本身**，所以不能拿大批量吞吐去换算，必须按这个形态量。

对照：岭回归实测 **87 秒**（0.406 ms/次）。

3 个种子的模型纯文本共 **18.5 MiB**（私榜 zip 要装得下）。

⚠️ 模型是在 **modulo 40（146,615 行）** 上训的，不是全量 —— 推理成本只取决于模型形状与调用形态，不取决于训练集大小。实测树形状：**平均深度 18.8（最大 32）、平均叶子数 63.0**（`num_leaves` 上限 63），这两个数就是用来核验这个迁移假设的。

## 怎么读

- **主办方没公布超时阈值**，所以这里只给绝对耗时，不自行判定「通过/不通过」。
  参照系：岭回归 87 秒跑完且从未超时，说明预算至少不止 87 秒。
- 成本随树的数量近似线性 → 可以用轮数换时间。`lgbm_blend` 里各折早停从 62 到 891 轮不等，最终模型该取多少轮是个**精度 vs 跑得完**的取舍。
- 种子数是线性因子：3 种子降到 1 种子直接省 3 倍，代价是失去种子平均的降方差。
- 若耗时不可接受，还有两条路：**减树**（降 `num_leaves` / 早停更严）、或**纯 numpy 树遍历**（`model_to_string` 是纯文本，也顺带解决评测端有没有lightgbm 的问题）。
